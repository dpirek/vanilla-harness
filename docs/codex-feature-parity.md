# Vanilla Harness and Codex: feature parity and opportunities

Reviewed September 21, 2026. Local revisions: Vanilla Harness `adb6a3f`; Codex `517f51a6f7`. This is a static source review, not a runtime or quality benchmark. “Partial” means the broad capability exists but an important Codex workflow or guarantee is missing. “Gap” means no first-class implementation was found in Vanilla Harness. Features behind Codex flags or tied to its hosted services are not assumed to be universally available.

## Executive assessment

Vanilla Harness already covers the basic coding-agent workflow: browser and terminal chat, workspace tools, exact edits, change history, structured conversation persistence and compaction, configurable permissions, MCP, skills, image input, and worker delegation. See its [README](../README.md), [agent loop](../lib/agent.js), [tool registry](../lib/tools/index.js), and [context store](../lib/conversation-context.js). Reimplementing these as headline parity features would add little value.

Codex's strongest transferable ideas are deeper execution boundaries, project-aware instructions, branchable isolated work, a stable client protocol, and better operational visibility. Its scale and hosted integrations do not need to be copied wholesale. Vanilla Harness's dependency-free server, embeddable web component, provider flexibility, presets, and A2A worker support are distinct strengths.

## What to build first

| Priority | Addition | Smallest useful milestone | Why it comes first |
| --- | --- | --- | --- |
| P0 | OS-backed tool sandbox | Run commands and local MCP processes in a workspace-scoped filesystem sandbox; deny network by default with explicit exceptions. Expose the effective policy in each approval prompt. | Current allow/ask/deny rules cannot contain a process after it starts. |
| P1 | Project instruction discovery | Read `AGENTS.md` from workspace root to active directory, cap bytes/tokens, show loaded sources in the UI, and reload on workspace change. | Low implementation cost, large improvement in repository-specific behavior. |
| P1 | Task worktrees | Create/list/select a Git worktree per session; report branch and dirty state; require an explicit action for deletion. | Makes parallel coding and review safer and easier to understand. |
| P1 | Conversation fork | Fork a session at a selected turn with a new session ID and copied context; separately offer guarded filesystem revert where edits are tracked. | Lets users explore alternatives without losing history. |
| P2 | Patch editing | Support a standard multi-file patch format with preview, stale-file checks, all-file preflight, and journaled application. | Improves edit precision while retaining current recovery guarantees. |
| P2 | Stable client protocol | Define versioned request/event schemas, resume semantics, and error codes; generate a small JavaScript client. | Enables editor extensions and external UIs without coupling them to DOM internals. |
| P2 | Run trace export | Record bounded structured events per turn and export JSON for reproducible bug reports. | Makes provider/tool failures easier to diagnose and compare. |
| P3 | MCP OAuth and richer metadata | Add browser-based authorization, token storage, connection status, and selective resource/prompt support. | Valuable for hosted MCP services, but more operationally complex. |

## Design lessons from Codex

1. **Treat policy and isolation as separate layers.** A tool permission decides whether an action may be attempted; a sandbox limits what the resulting process can reach. Vanilla's current policy is useful but cannot enforce the latter.
2. **Keep context bounded and attributable.** Codex's project instruction loading and trace model suggest recording where each injected instruction came from and bounding its size. Vanilla already compacts history; the next step is transparent context composition.
3. **Make session state a client-facing contract.** Forks, resumes, approvals, and events work best when represented as stable operations with IDs, rather than UI-specific behavior. This also simplifies CLI and browser parity.
4. **Separate conversation history from workspace state.** Forking a chat does not copy files; undoing a tracked edit does not rewind a conversation; a Git worktree provides a separate filesystem. Present these as distinct actions.
5. **Instrument the agent loop before broadening integrations.** Tool and provider timing, usage, and approval outcomes will show which features actually improve task completion.

## Review limits

The two local checkouts were inspected without running either application or its tests. Absence claims mean no first-class path was found in the inspected source, not that the behavior is impossible through shell commands or third-party MCP tools. Codex is a much larger product; feature presence does not establish reliability or suitability for Vanilla Harness. The existing [OpenCode parity report](opencode-feature-parity.md) describes a different comparison and should not be read as Codex evidence.
